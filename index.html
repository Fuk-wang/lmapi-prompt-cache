前缀稳定为什么能省钱：
缓存只认得前面那段没变的部分

大模型的注意力需要把输入完整读一遍。如果每次都重读同一段 2400 token 的说明文档，就要为它付 100 次钱。 前缀缓存（Prompt Caching / Prefix Caching）把「读过的部分」留在显存里—— 前提是那部分一个字节都没变。前缀里改一个字，从那个位置往后的缓存全部作废。

实测调用 14 次（deepseek-flash） 缓存命中单价是未命中的 1/50 实测命中值均为 64 的整数倍 花费 $0.0023（全部实测跑出来）

本页所有数字都来自真实 API 调用，原始 JSON 与探针脚本在仓库 experiments/ 目录， 可照着复现（见页末引用与实测环境）。凡属插值或推算的地方，页面都会显式标注。

01 · 原理

缓存匹配是「前缀匹配」，不是「相似匹配」

服务端把已经算过的 token 序列（KV 缓存）按前缀单元存下来。新请求进来时，从第一个 token 开始逐个比对， 一直比到第一个不同的位置为止——那个位置之前的 token 全部命中，之后的全部要重算。 没有「部分相似」「语义相同」这种余地。

命中区 / CACHED PREFIX
不动的那一段：系统提示词、工具定义、知识库、few-shot 例子
易变尾部 / VOLATILE TAIL
每轮都在变的那一小段：用户这回的问题

两种流派，规则不一样

维度DeepSeek 自动缓存Anthropic 显式断点
怎么开默认开启，不改代码请求里加 cache_control
缓存在哪系统按前缀单元自动落盘指定的断点之前
写入成本无额外费用5 分钟 TTL 为 1.25x，1 小时为 2x
命中成本约为未命中的 1/50基础输入价的 0.1x
存活时间由系统策略决定5m 或 1h（要显式指定）

数据来源：DeepSeek 上下文硬盘缓存、 DeepSeek 定价、 Anthropic Prompt caching。

05 · 工程清单

让前缀稳定下来的六条做法

每一条都标了来源：官方文档，或 Hermes Agent 源码里的真实实现。

  1. 把不变的东西全部放前面，把每轮会变的挤到最后。 系统提示词、工具定义、知识库、few-shot 例子在最前，本轮提问在最后。这是实测里 90%+ 命中率的来源。 DeepSeek 文档Anthropic 文档
  2. 绝不要在前缀里放时间戳、随机 id、请求序号、datetime.now()。 它们每轮都变，而且位置一旦靠前，后面所有内容全部作废——实测中只在 11% 处改了一个数字，命中就只剩 128 token。 实测
  3. 工具定义 / few-shot 例子的顺序和序列化格式必须固定。 同一个工具集打乱顺序、或者 dict 键顺序变了，字节就变了，前缀判定为不同。 Anthropic 文档
  4. 多轮对话里不要回头改写历史消息。 压缩上下文、动态插入记忆、热更新系统提示词都属于「重写前缀」，会让整段缓存作废。 Hermes 源码
  5. 把大而稳定的脚手架和易变尾部在同一段文本里显式分开。 与其在运行时用分隔符去猜「边界在哪」，不如让构建这段文本的代码自己声明边界。 Hermes 源码
  6. 用 usage 里的命中字段做监控，而不是凭感觉。 DeepSeek 返回 prompt_cache_hit_tokens / prompt_cache_miss_tokens； Anthropic 的 usage 里有 cache write / read 两类计数。命中率掉了就是有人动了前缀。 DeepSeek 文档Anthropic 文档
06 · 参考实现

成熟实现是怎么处理的：Hermes Agent 的前缀缓存策略

前面讲的是实测规律，这里看一个真实实现怎么处理同一件事。规律是：前缀中段一改，命中归零， 而且运行时想用启发式去猜「稳定边界在哪」很容易猜错。Hermes 的做法正好相反—— 它不让运行时去猜，而是让构建者显式声明。

① 缓存是有「不变量」地位的

在 hermes-agent 仓库根目录的 AGENTS.md 里，第一条设计不变量就是它： 

// hermes-agent/AGENTS.md
Per-conversation prompt caching is sacred.
A long-lived conversation reuses a cached prefix every
turn. Anything that mutates past context, swaps
toolsets, reloads memories, or rebuilds the system
prompt mid-conversation invalidates that cache and
multiplies the user's cost.
// 唯一的例外：上下文压缩（compression）

对应上面工程清单的第 4 条。区别是：清单里那是一条建议，这里把它写成了代码约束—— 改动历史的那些斜杠命令默认「下次会话生效」，要立刻生效得显式加 --now。

② 断点放在哪：四个位置，一个 TTL

agent/prompt_caching.py 的模块注释直接写了默认布局： 

// agent/prompt_caching.py
"""Anthropic prompt caching strategy — pure functions.
Default layout: 4 cache_control breakpoints — the static
system prefix, the end of the system prompt, and the
last 2 non-system messages (without a static prefix:
one system breakpoint plus the last 3 messages).
All markers share one TTL (5m or 1h).
"""

这几行解释了「缓存该切在哪」的工程答案：放在稳定段的末尾，而不是每轮都在动的头上。 和实测里「命中只到第一个差异为止」是同一件事的两面。

③ 最漂亮的一处：不让运行时猜边界

技能/定时任务把一大段静态脚手架和一小段易变尾部拼成一个 user 消息字符串。 问题是：运行时看到这串字符，怎么知道尾部从哪开始？agent/prompt_cache_boundary.py 的答案是不猜： 

# agent/prompt_cache_boundary.py
"""Builder-declared stable prefixes for Anthropic prompt caching.

Skill/webhook/cron builders concatenate a large static scaffold
with a small volatile tail into one user-message string. Only the
builder knows where the tail begins, so it registers the stable
prefix here and the cache planner places a breakpoint at that
boundary. Re-parsing marker strings at request time is deliberately
avoided: markers can legitimately appear inside skill bodies, and any
delimiter heuristic then shrinks the cached prefix or absorbs volatile
bytes.
"""

def register_stable_prefix(prefix: str) -> None: ...
def find_stable_prefix(content: str) -> Optional[str]: ...

这段注释和前面的实测是同一件事的另一面：启发式猜边界，猜错的代价是把易变字节吸进缓存前缀 （于是每次都 miss），或者把稳定字节排除在外（于是白付钱）。 所以它选择让 agent/skill_commands.py 在拼字符串时顺手 register_stable_prefix()， 缓存规划器再把断点打在那个边界上。

④ 前缀的体积本身也被当成成本来管

系统提示词会被反复重发，所以它的每一行都是「每个会话都要付一次」的。agent/prompt_builder.py 里两条注释就是照这个逻辑写的： 

# agent/prompt_builder.py:378
Ships in every cached prompt — keep tight.

# agent/prompt_builder.py:404
Short on purpose — shipped in the cached system prompt to every user, every session.
Token cost is paid once at install and amortised across all sessions via prefix caching.
Keep it tight.

这和 04 节的计算器是同一件事的两面：稳定前缀越长，命中省下的绝对金额越多； 但任何塞进前缀的内容——哪怕是一句没人读的旧说明——也都进了每一次调用。

两类常见故障与对应做法

常见故障Hermes 源码里的应对
前缀中段改一个词 → 命中率从 91.3% 掉到 0% 把「不改历史」写成不变量，改历史的命令默认延迟到下次会话生效
命中只到第一个差异为止，且按 64 token 向下取整 断点显式打在稳定段末尾；缓存规划器只在这些位置切

07 · 结论

这个知识点该用哪一层解决？

答案：Runtime（运行时 / 架构层），不是 Prompt 层。

写「请你保持前缀稳定」这种句子进 prompt 是没用的——模型不控制消息数组怎么拼。 真正决定命中率的是调用方的代码：谁在什么位置塞了时间戳、工具定义有没有稳定的序列化、 上下文压缩时动不动历史消息。这些都在运行时。

所以工程清单里那几条应当落实成代码约束， 而不是写进给模型的提示词里。
